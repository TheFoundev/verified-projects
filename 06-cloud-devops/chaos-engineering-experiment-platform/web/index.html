Break something on purpose, then check that the service held.

Chaos defines an experiment as a list of actions - delay, kill or stress - against a target service, applies them one by one and writes a timeline of applied, recovered and rolled-back events. Before the first action and after every recovery it checks a steady-state hypothesis, and it stops and rolls the actions back when the hypothesis breaks.

What it does

The capabilities

Every panel below is served by the real API of this project — nothing here is a mock-up.

⚙

Three faults

Validate accepts delay, kill and stress; every other kind is refused.

⚖

Steady state

The hypothesis is checked before the first action and after every recovery.

↻

Rollback

When the hypothesis breaks the applied actions are recovered in reverse order.

◷

Timeline

Every apply, recovery and rollback is an Event with a real timestamp.

▤

Two stores

MemoryStore keeps the results in memory, FileStore writes them to a JSON file.

⧉

Pluggable executor

The runner never talks to Kubernetes; it goes through the FaultExecutor interface.

Architecture

How it works

chaos.go holds the engine. Validate accepts the action kinds delay, kill and stress and checks the hypothesis, and Compare applies the lt, gt and eq operators. Runner.Run walks the actions: it calls FaultExecutor.Apply, waits for the duration of the action, calls Recover and appends an Event for every phase; when the hypothesis breaks it recovers the applied actions in reverse order and marks the result as aborted. The executors are DryRunExecutor, which changes nothing, and LocalExecutor, which really waits, burns CPU and sends SIGTERM to a process id. The results are kept by a Store: MemoryStore in memory and FileStore in a JSON file.
