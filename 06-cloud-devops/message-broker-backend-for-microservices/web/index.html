A broken order never blocks the queue.

An Erlang/OTP order-processing backend on RabbitMQ quorum queues: publisher confirms, a consumer with a retry ladder, a Prometheus endpoint and a small HTTP interface.

This is an Erlang/OTP service, not a hosted product. It is part of the Foundev portfolio: a self-contained repository with its own tests and README. The page you are reading is a project console — the numbers below are computed from the repository, and the demo runs the project's own command.
What it does

The capabilities

Every panel below is served by the console's real API — nothing here is a mock-up.

⇉

Orders over HTTP

POST /orders publishes to the orders exchange with an idempotency key and publisher confirms.

◈

A four-step pipeline

Validate, reserve inventory, charge and fulfil run in order for every delivery.

↺

Transient versus terminal

Failures are classified; transient faults climb a retry ladder and terminal ones go to the dead-letter queue.

⛨

Supervised connection

The AMQP connection reconnects with backoff and re-declares the topology after a reconnect.

◷

Prometheus metrics

Queue depth, retries and outcomes are exposed for scraping.

⌗

One supervisor per process

The OTP tree keeps the connection, publisher and consumer independently restartable.

Architecture

How it works

mbb_connection owns the AMQP connection and channel, mbb_topology declares the exchange, queues and bindings idempotently, and mbb_publisher publishes with confirms. mbb_consumer consumes with a prefetch window, classifies each outcome and settles the delivery as ack, retry or dead letter. mbb_order is the pure domain layer: the pipeline, the JSON codec and the idempotency key, with no side effects.
